## 1. `noteId()` валідує слабше, ніж написано в його ж комментарі ⚠️ ВІДКРИТО

- **Що просив:** Task B, пункт 3 — «валідуйте на сервері», включно з
  ідентифікатором у шляху.
- **Що видав:** `app/src/app.js`, хелпер `noteId()` з комментарем
  «"abc", "-1" and "1.5" are not ids» — тобто заявлена сувора перевірка.
  Реалізація через `Number(raw)` + `Number.isInteger`. Фактично:

  ```
  "0x1"  -> 1        "0b11" -> 3        "1e2" -> 100       " 2 " -> 2
  ```

  Отже `GET /api/notes/0x1` віддає нотатку 1. **Не дірка в безпеці** — усі
  запити до одного рядка й далі обмежені `AND user_id = ?`.

- **Як помітив:** не тестами. Тести перевіряли рівно ті випадки, які названі в
  комментарі (`abc`, `-1`). Помітив, перечитуючи код.
- **Як полагодив:** **ще ні.** Пропозиція — відсікати все, що не є десятковим
  записом, до перетворення:

  ```js
  if (!/^\d+$/.test(String(raw))) return null;
  ```

  плюс тести на `0x1` і `1e2` → 400.
- **Чому агент так зробив (гіпотеза):** `Number()` — ідіоматичне перетворення в
  JS, а в парі з `Number.isInteger` воно *виглядає* суворим;

## 2. Тести написані після коду, їхня «зубастість» не доведена ⚠️ ВІДКРИТО

- **Що просив:** Task B — «наявні 9 тестів мають лишитись зеленими; додайте
  свої».
- **Що видав:** 12 тестів на `PATCH /api/notes/:id/archive`, написані **після**
  реалізації. Усі зелені з першого прогону.
- **Як помітив:** під час Task C, коли робив мутаційну перевірку (прибрав
  `AND user_id = ?` і подивився, чи почервоніє тест). Це був **перший раз**,
  коли хоч один тест показав червоне. Решта — ніколи не бачили зламаного
  коду, тобто про них невідомо, чи вони щось перевіряють.
- **Як полагодив:** **частково.** Доведено лише
  `will not archive someone else's note` (і два тести з Task C, які писались
  перед правкою). Пропозиція — по черзі ламати кожне правило (наприклад,
  прибрати перевірку `typeof … !== "boolean"`) і переконуватись, що червоніє
  саме відповідний тест.
- **Чому агент так зробив (гіпотеза):** зелений набір емоційно читається як
  доказ. Коли тест пишеться після коду, він описує **те, що код робить**, а не
  те, що код **має** робити, — і форма «усе зелено» приховує, що питання не
  ставилось.

## 3. Оголошував успіх, не подивившись на відповідь сервера ✅ полагоджено

- **Що просив:** Task A — контрол архівування з доступними оголошеннями.
- **Що видав:** у `app/public/app.js` обробник видалення робив
  `await fetch(...)`, потім `load()`, потім
  `say("Нотатку «X» видалено.")` — **без перевірки `res.ok`**. Тобто 404 (нотатку
  вже видалено, або вона чужа) озвучувався скрінрідеру як успіх. Та сама форма на
  створенні: заголовок із самих пробілів проходить HTML `required`, сервер
  відповідає 400, а UI тихо чистив поля й не казав нічого.
- **Як помітив:** перечитуючи код.
- **Як полагодив:** усі три обробники (архів, видалення, створення) перевіряють
  `res.ok`; на невдалому створенні введений текст зберігається, фокус вертається
  в поле. Перевірено в браузері: статус читає
  «Не вдалося додати нотатку: title is required».
- **Чому агент так зробив (гіпотеза):** без поняття ;)

- **Як полагодив:** пояснив причину, закомітив свідомоі зафіксував
  обґрунтування для тіла PR.
- **Чому агент так зробив (гіпотеза):** задача була сформульована як «запусти

## Що агент зробив ДОБРЕ там, де я чекав проблем

- **Не «полагодив» засіяну діру завчасно.** Найбільший ризик був у тому, що
  агент побачить `WHERE id = ?` у `GET /api/notes/:id` під час Task A або B і
  виправить «між іншим» — це знищило б увесь сенс Task C2. Діра лишилась
  недоторканою до Task C, а в планах було явно написано, чому.
- **Умова власника опинилась у самому запиті**, а не перевіркою після `SELECT`;
  ні разу не з'явився шаблон «дістати рядок →
  `if (note.user_id !== req.userId)`». І 404 замість 403 — без підказки, що чужа
  нотатка взагалі існує.
- **Міграція врахувала наявну базу.** `CREATE TABLE IF NOT EXISTS` нічого не
  робить із наявним файлом — агент додав `ALTER TABLE` під перевіркою
  `pragma_table_info` і перевірив це на базі, створеній **до** зміни схеми.
