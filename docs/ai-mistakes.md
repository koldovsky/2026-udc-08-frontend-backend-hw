# Що AI зробив не так (Task D)

**Інструмент і модель:** Claude Code, переважно Claude Sonnet 5 (на початку сесії коротко був перемкнений Claude Fable 5).

## 1. Викликав видалений API Playwright, побудований «з пам'яті»

- **Що просив:** перевірити Task A в браузері через DOM/дерево доступності, а не лише скріншотом (вимога з `docs/walkthrough.md`).
- **Що видав:** написав скрипт для Playwright з викликом `page.accessibility.snapshot({ interestingOnly: true })` — це метод старіших версій Playwright. Встановлена версія — 1.63.0, де `page.accessibility` вже видалено.
- **Як помітив:** запустив скрипт — одразу впав з `TypeError: Cannot read properties of undefined (reading 'snapshot')`, стек показав точну причину.
- **Як полагодив:** переписав на актуальний API — `page.locator("body").ariaSnapshot()`, який повертає той самий YAML-подібний знімок дерева доступності. Після цього скрипт відпрацював і дав реальні дані (з'явились у звіті: `button "Архівувати нотатку «Список покупок»"` тощо).
- **Чому агент так зробив (гіпотеза):** навчальні дані містять і старий (`page.accessibility`), і новий (`ariaSnapshot`) API одразу для кількох версій Playwright; без перевірки встановленої версії агент згадав перший, що спав на думку, замість того щоб спершу глянути `node_modules/playwright/package.json`.

## 2. Продублював `describe` замість того, щоб розширити наявний

- **Що просив:** додати тести на `archived`-поле та новий `PATCH /api/notes/:id/archive` ендпоінт (Task B).
- **Що видав:** у `app/test/api.test.js` вже був блок `describe("GET /api/notes", ...)` (рядок 20, з двома тестами на список нотаток власника). Замість того, щоб додати туди ще один `it`, агент дописав **другий, окремий** блок `describe("GET /api/notes", ...)` (рядок 69) із тестом на булеве поле `archived`. Файл технічно валідний — Vitest не забороняє однакові назви `describe` — але це структурне сміття, яке ускладнює читання файла.
- **Як помітив:** не тест і не браузер — жодний тест не впав через дублікат, бо Vitest виконує обидва блоки незалежно. Помітив вручну під час підготовки Task D: `grep -n 'describe("GET /api/notes"' test/api.test.js` показав два збіги.
- **Як полагодив:** злив тест з другого `describe` у перший і видалив дублікат-обгортку. `npm test` лишився 18/18 зеленим — фіксую тут саме як приклад «тест не зловив би це ніколи», бо дублікат не впливав на проходження, лише на читабельність.
- **Чому агент так зробив (гіпотеза):** редагував файл через послідовні `Edit`-вставки в кінець існуючих секцій, орієнтуючись на найближчий сусідній блок (`PATCH .../archive`), а не сканував файл на предмет вже наявного `describe` з такою ж назвою перед тим, як його створити.

## 3. Прибрав статичний текст порожнього стану, залишивши це виключно на JS

- **Що просив:** дати притомний порожній стан для вкладок «Активні» / «Архів» (Task A).
- **Що видав:** в `app/public/index.html` було `<p id="empty" hidden>Нотаток поки немає.</p>` — текст був прямо в HTML, видимий навіть якщо скрипт не встигне/не зможе виконатись. Агент замінив на `<p id="empty" hidden></p>` і переніс текст у `app.js` (`emptyMessage()`), бо тепер повідомлення різне для двох вкладок.
- **Як помітив:** не сталося на практиці (скрипт завжди відпрацьовує), але при перегляді дифу для Task D видно: `git diff app/public/index.html` показує рядок з видаленим текстом і без жодного fallback на випадок, якщо `<script type="module">` не завантажиться (заблокований CSP, старий браузер без підтримки ES-модулів тощо).
- **Як полагодив:** повернув нейтральний дефолт у HTML (`<p id="empty" hidden>Нотаток поки немає.</p>`); `app.js` як і раніше перезаписує його через `empty.textContent = emptyMessage()` при кожному рендері, тож дефолт лишається лише резервним станом на випадок відмови скрипта, а не єдиним джерелом тексту.
- **Чому агент так зробив (гіпотеза):** оптимізував логіку одного джерела правди (текст залежить від `view`), не тримаючи в увазі, що статичний HTML-текст був і резервним станом на випадок відмови скрипта — це вимога, якої не було явно сформульовано в задачі.

## Що агент зробив ДОБРЕ там, де я чекав проблем

- **Авторизація нового ендпоінта (Task C1) агент написав правильно ще в Task B, без нагадування.** `PATCH /api/notes/:id/archive` від самого початку мав умову власника прямо в SQL-запиті (`WHERE id = ? AND user_id = ?`), хоча про це прямо просили лише в Task C. Це саме та помилка («перевірка після того, як рядок уже дістали», або й гірше — жодної перевірки), яку задача навмисно засіяла в іншому ендпоінті — і тут агент її не повторив.
- **Дотримався порядку «відтвори → тест червоний → фікс → тест зелений»** для засіяної діри (Task C2), а не просто одразу переписав код. Спершу за допомогою `curl` показав реальний витік (`{"user_id":2,"body":"пароль від сейфа: 1234"}` при запиті від імені іншого користувача), потім написав тест і перевірив, що він падає (`expected 404, got 200`), і лише після цього зробив правку.
- **Не піддався спокусі мовчки "полагодити" провалені тести**, коли `npm test` спершу впав через несумісність `better-sqlite3` з Node 26 — перевірив (`git stash` + прогін тестів без своїх змін), що це середовищна проблема, а не регресія від його правок, і чесно про це сказав, замість видавати бажане за дійсне.

## Що я перевіряв і воно виявилось чистим

- **Нечисловий id в URL** (`GET /api/notes/abc`, `PATCH /api/notes/abc/archive`) — не валиться в 500, `better-sqlite3` коректно обробляє `NaN` як параметр, обидва ендпоінти віддають чистий `404`.
- **Міграція схеми на реальному, не тестовому файлі бази.** Перевірено не лише на `:memory:` з тестів, а й на справжньому `notes.db`, який лишився від попереднього запуску сервера до додавання колонки `archived` — після рестарту сервера колонка додалась (`ALTER TABLE ... ADD COLUMN`), обидві засіяні нотатки Олі лишились на місці з `archived: false`.
- **Відповідь нового ендпоінту й полагодженого `GET /api/notes/:id` не містить `user_id`** — перевірено прямим `curl`, а не лише читанням коду.
