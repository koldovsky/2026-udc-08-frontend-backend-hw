# Що AI зробив не так (Task D)

**Інструмент:** Claude Code
**Модель-імплементатор:** Sonnet 5
**Модель-аудитор:** Opus 5 (окрема сесія без контексту імплементатора)

**Середовище.** На Node 26 `better-sqlite3@11` не збирається — у V8 прибрано
API, на яке спирається його нативний модуль. Підняв до `^13.0.3`: це вже наявна
залежність, не нова, і лок при цьому **схуд** на все дерево `prebuild-install`
(−30 транзитивних пакетів). `better-sqlite3@13.0.3` декларує
`engines: { node: ">=22" }`, тобто нижню планку воркшопу (Node 22+) тримає.
Чи збирається **стартовий** лок на Node 22, я не перевіряв — під рукою був
лише Node 26, тож це єдине, що тут стверджується з доказом.

**Як збиралися докази.** Кожну задачу після «готово» перевіряла окрема сесія,
яка не бачила ані промптів імплементатора, ані його рішень. Перевірка — не
читання дифу, а запуск: `npm test`, живий сервер + `curl`, headless Chromium
(Playwright) для DOM і дерева доступності, обчислення контрасту з computed
styles, і **мутаційне тестування** — навмисне ламання джерела, щоб побачити,
чи справді червоніє тест, який нібито це покриває.

Головний висновок наперед: **код агента витримав усі мутації. Те, що
знаходилось — це відсутні тести, а не зламана логіка.** Один виняток — №1,
де «працює» в браузері й «працює» — різні речі.

## 1. Фіча, яка «працює» в браузері, але зникає після reload

- **Що просив:** Task A — UI архівування нотатки (кнопка, фільтр, порожній
  стан). Колонка в базі — це Task B, окрема задача.
- **Що видав:** `app/public/app.js` — стан архіву жив у `const archivedIds =
  new Set()`, тобто лише в пам'яті вкладки. Жодного запиту на сервер.
  Візуально фіча була повністю робоча: кнопка перемикає, фільтр фільтрує,
  порожній стан з'являється.
- **Як помітив:** headless Chromium. Заархівував нотатку, натиснув
  **reload**, відкрив вкладку «Архів»:

  ```text
  after archive, Активні items: 1
  Архів items: 1
  >>> RELOAD
  after reload, Активні items: 2     <- нотатка повернулась
  after reload, Архів items: 0       <- архів порожній
  ```

  Ручна перевірка «кнопки є, працює» цього не ловить — треба саме
  перезавантажити сторінку.
- **Як полагодив:** Task B: колонка `archived`, ендпоінт
  `PATCH /api/notes/:id/archive`, `archivedIds` видалено, UI читає й пише
  реальне поле. Після цього той самий сценарій: `after reload, Архів items: 1`,
  і стан переживає навіть рестарт процесу сервера.
- **Чому агент так зробив (гіпотеза):** він виконав скоуп **буквально
  правильно** — walkthrough справді відносить базу до Task B, і агент сам
  залишив у коді чесний маркер:

  ```js
  // TODO(Task B): `archived` isn't a real column yet, so this Set is the only
  // place archive state lives — it resets on reload/user switch.
  ```

  Тобто це не галюцинація. Ризик тут людський: якби Task A здавалась як
  «готово, перевірив у браузері», у PR поїхала б фіча-декорація. Сам агент
  про це не попередив у відповіді — попередження було лише в коментарі в коді.

## 2. Доступність: формально виконано, фактично ні

Task A прямо вимагає «справжня `<button>` з текстом або `aria-label`, розмір
цілі, контраст». Формально все було зроблено. Два дефекти пережили це
формулювання.

- **Що видав:**
  1. У списку з двох нотаток — чотири кнопки з двома accessible names на всіх:

     ```text
     button "Архівувати"   button "Видалити"
     button "Архівувати"   button "Видалити"
     ```

     Користувач скрінрідера, який перелічує кнопки сторінки, не має способу
     зрозуміти, яка кнопка до якої нотатки.
  2. Межі інтерактивних контролів — `border: 1px solid #8884`.
- **Як помітив:** дерево доступності через Playwright (`ariaSnapshot`) для
  першого; для другого — порахував контраст із computed styles відносно
  реального canvas у двох темах:

  | | light | dark | вимога |
  |---|---|---|---|
  | межа `button` / `input` — `#8884` | **1.33** | **1.46** | 3.0 (WCAG 1.4.11) |

  Текст при цьому був чистий (19.6:1 на кнопці, 7.0:1 на даті), розмір цілі —
  44×109 px, тобто навіть AAA (2.5.5). Провалився саме той критерій, який
  око не бачить.
- **Як полагодив:**
  1. `aria-label` з назвою нотатки: `Архівувати: Список покупок`. Після фіксу
     — 4 унікальні accessible names на 4 кнопки.
  2. `#8884` → `#888e` на `button` і `input`: **3.19** (light) / **4.74**
     (dark). Межу картки `li` лишили `#8884` — це декор, а не контрол, під
     1.4.11 не підпадає.
- **Чому агент так зробив (гіпотеза):** вимогу «контраст» він прочитав як «не
  зіпсуй контраст», а не «виміряй наявний». Рядок з `border: #8884` він **сам
  редагував** (додавав `min-height` для розміру цілі) і не перевірив те, що
  редагує. Успадковане з засіяного репо — але пройшло через його руки.
- **Побічно, чесно на користь агента:** він поставив `aria-label` так, що
  видимий текст лишився на початку рядка (`Архівувати: …`). Це зберігає
  WCAG 2.5.3 *Label in Name* — голосове керування «натисни Архівувати» далі
  спрацьовує. Його про це не просили; `aria-label="Архівувати нотатку
  Список покупок"` зламав би цей критерій.

## 3. Двічі: тест, який не питає того, що нібито перевіряє

Це рівно та пастка, про яку воркшоп, — тільки не в засіяному коді, а в
**нових** тестах.

### 3a. Міграція бази без жодного покриття

- **Що видав:** `app/src/db.js` отримав коректну міграцію
  (`PRAGMA table_info` → `ALTER TABLE notes ADD COLUMN archived`). Тести —
  три нові на ендпоінт архівування, **жодного на міграцію**.
- **Як помітив:** весь набір працює на `:memory:`, а нова база завжди
  отримує колонку з `CREATE TABLE`. Отже гілка `ALTER TABLE` **ніколи не
  виконується в CI** — єдиний шлях у коді, здатний знищити чужі дані, мав
  нуль покриття. Перевірив руками: зібрав файл БД зі *старою* схемою, вставив
  рядки, відкрив новим `createDb()` — дані вижили. Але цього доказу не було
  в репозиторії.
- **Як полагодив:** два тести (`createDb migration`), які будують тимчасовий
  файл на старій схемі й перевіряють збереження рядків + ідемпотентність.
- **Мутаційна перевірка, що тест не декоративний:**

  | що зламав | результат |
  |---|---|
  | видалив блок `ALTER TABLE` | `adds archived without losing pre-existing rows` → **FAIL** |
  | прибрав охорону `if (!hasArchived)` | **усі 14 тестів FAIL** (`duplicate column name`) |

### 3b. Половина фіксу Task C лишилась без тесту

- **Що видав:** засіяну діру полагоджено правильно (див. розділ «добре»), і
  доданий тест `will not read someone else's note`. Фікс мав **дві** частини:
  умова по власнику **і** прибрати `user_id` з відповіді. Тест покривав лише
  першу.
- **Як помітив:** мутація. Повернув `user_id` у `SELECT`, залишивши
  авторизацію на місці → **15/15 зелені**. Тобто половина фіксу могла
  тихо відкотитись із зеленим CI.
- **Як полагодив:** `expect(res.body).not.toHaveProperty("user_id")` на
  читанні однієї нотатки та аналогічна перевірка на списку.
- **Мутаційна перевірка після фіксу:**

  ```text
  user_id назад у GET /api/notes/:id
    × returns the caller's own note
      → expected { id: 1, user_id: 1, …(4) } to not have property "user_id"
  user_id назад у GET /api/notes
    × returns only the caller's own notes
  ```

- **Чому агент так зробив (гіпотеза):** «полагодь авторизацію» він прочитав
  як «закрий доступ». Guardrail «не віддавай зайвого» — окреме речення в
  AGENTS.md, і в тест воно не перетворилось. Показово, що в **своєму**
  ендпоінті (`PATCH .../archive`) він таку перевірку написав одразу
  (`not.toHaveProperty("user_id")`) — тобто знав патерн, але не переніс його
  на маршрут, який чинив.

## Що агент зробив ДОБРЕ там, де я чекав проблем

Перевірено мутаціями й живими запитами, а не на віру.

- **Засіяну діру полагодив у самому запиті, а не після вибірки.**
  `WHERE id = ? AND user_id = ?`, а не `if (note.user_id !== req.userId)`.
  Саме те, чого вимагає Task C. Мутація (повернув оригінальний маршрут
  дослівно) → `will not read someone else's note` **FAIL**. Тест справді
  червоніє на коді до правки.
- **Серверна валідація реально серверна** — з одним винятком, знайденим
  пізніше (див. нижче). 11 некоректних запитів, усі відбиті сервером:
  `"yes"`, `"true"`, `1`, `null`, `{}`, порожнє тіло, без `content-type`,
  масив → **400**; id `abc` / `999` / `1 OR 1=1` → **404**; без заголовка та
  `x-user-id: 0` → **401**.

  > **Виправлення до цього пункту.** Пізніший незалежний аудит додав 12-ту
  > пробу, якої тут не було: `x-user-id: 99` — валідний за формою id
  > **неіснуючого** користувача. `currentUser` пропускав будь-яке додатне ціле,
  > тож `POST /api/notes` падав на `FOREIGN KEY constraint failed` і Express
  > віддавав **500 зі стектрейсом і абсолютними шляхами у тілі відповіді**, а
  > `GET /api/notes` повертав **200 `[]`** неіснуючому користувачеві. Тобто
  > твердження «усі некоректні запити відбиті» було завузько перевірене: я
  > перебирав **форму** заголовка, але не **існування** користувача. Полагоджено
  > в `currentUser` (перевірка рядка в `users` → **401**) і закрито пробами в
  > `authz.test.js`. Залишаю початкове формулювання видимим: помилка була в
  > повноті моєї перевірки, а не в коді агента.
  >
  > І друга річ того самого класу, знайдена вже при повторній перевірці фіксу:
  > сам по собі 401 діри не закривав, бо **будь-яка** помилка, що вилітає з
  > хендлера, доходила до дефолтного обробника Express, а той рендерить стек у
  > тіло відповіді. Найпростіший тригер — зіпсований JSON: `{oops` давав **400**
  > з HTML-сторінкою, `SyntaxError` і шляхами в `node_modules`. Тобто я полагодив
  > один тригер, а не причину. Причина — відсутність catch-all обробника; додано
  > один `app.use((err, …))`, який віддає `{ error }` і ніколи не `err.stack`.
  > Урок той самий, що й у розділі 3: фікс, перевірений лише на тому вході, що
  > його спричинив, лишає клас відкритим.
- **Підробити власника через POST не вийшло.** Надіслав як Оля
  `{"title":"forged","user_id":2,"id":999,"archived":true}` → створено `id=4`,
  власник **Оля**, `archived=false`. Поля з тіла проігноровані.
- **`UPDATE … RETURNING` через `.get()` справді комітить.** Це був мій
  головний підозрюваний після рефакторингу (в better-sqlite3 мутуючий запит
  через `.get()` — типове місце для тихої втрати запису). Перевірив рестартом
  процесу: `GET after RESTART: 1:true` — запис на диску.
- **Міграція неруйнівна та ідемпотентна** — підтверджено на штучній старій БД
  (рядки, значення, `archived=0` за замовчуванням, без повторного сідування).
- **Скоуп не розповзався.** Коли просив тільки тести — джерело лишилось
  байт-у-байт незмінним (`diff` проти знімка). Бандлер, фреймворк, зайві
  залежності не з'явились жодного разу.

## Що я перевіряв і воно виявилось чистим

Список зроблено для того, щоб «нічого не знайшов» щось означало.

| Перевірка | Як | Результат |
|---|---|---|
| Кожен маршрут «не тим користувачем» | `curl` по всіх 5 маршрутах | `GET/:id`, `PATCH/archive`, `DELETE` → **404**; список віддає лише своє |
| Ті самі маршрути власником | `curl` | **200**, працює |
| Нотатка жертви після спроб чужого | `GET` як Тарас | не змінена, не видалена |
| Без автентифікації | усі маршрути | **401** |
| SQL-ін'єкція в `:id` | `1 OR 1=1` | **404**, запити параметризовані |
| Форма відповіді | ключі всіх маршрутів | `id, title, body, archived, created_at` — **`user_id` ніде** |
| Persistence архіву | reload сторінки + рестарт сервера | переживає обидва |
| Перемикання користувача в UI | Playwright | списки не змішуються |
| Помилки в консолі браузера | весь сценарій A→B→C | **0** |
| Контраст тексту | computed styles, 2 теми | 19.6 / 10.4 / 7.0 — усе ≥ 4.5 |
| Розмір цілі | getBoundingClientRect | 44 px — проходить навіть AAA |
| Регресія засіяного набору | `npm test` після кожної задачі | 9 → 12 → 14 → 15 → 16, жоден із 9 початкових не зламано |
| Тимчасові файли тестів | `ls $TMPDIR/ws08-db-*` | прибираються, не течуть |
| Секрети / `.env` / `*.db` у комміті | `git status`, `git check-ignore` | чисто, `notes.db` і `*.local` ігноруються |

**Мутацій проведено 9.** Вісім з них одразу завалили саме той тест, який мав
би їх ловити. Дев'ята — повернення `user_id` у відповідь при збереженій
авторизації — пройшла з зеленим набором (розділ 3b); після доданої перевірки
ловиться теж. Тобто станом на зараз усі 9 покриті.

Ще 4 мутації — вже проти набору з Task E — у
[`task-e-bonus.md`](./task-e-bonus.md). Одна з них (`POST` бере `user_id`
з тіла запиту) проходить повз увесь `api.test.js` і падає лише на новому
свіпі: десята прогалина в покритті, знайдена вже після того, як Task A–C
вважались закритими.
