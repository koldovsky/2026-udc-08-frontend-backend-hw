# Task B — API і база

Серверна частина архівування: колонка, ендпоінт, валідація.

## 1. Зміна схеми

Додано колонку `archived` до таблиці `notes` — `app/src/db.js`.

```sql
ALTER TABLE notes ADD COLUMN archived INTEGER NOT NULL DEFAULT 0
```

SQLite не має булевого типу, тож `INTEGER` з `0/1` — звичайна для нього форма.

**Чому `ALTER TABLE`, а не правка `CREATE TABLE`.** `CREATE TABLE IF NOT
EXISTS` не чіпає таблицю, яка вже існує: дописування колонки прямо в нього
подіяло б лише на порожню базу. У розробника з уже створеним `notes.db`
(`npm run dev` створює його при першому запуску) таблиця лишилася б старою, і
застосунок падав би на `no such column: archived`. `ALTER TABLE` натомість
додає колонку до наявних даних, не руйнуючи їх — вимога «схема не має
знищувати наявні дані».

Міграція виконується один раз, під перевіркою:

```js
const hasArchived = db
  .prepare("SELECT COUNT(*) AS n FROM pragma_table_info('notes') WHERE name = 'archived'")
  .get().n > 0;
if (!hasArchived) {
  db.exec("ALTER TABLE notes ADD COLUMN archived INTEGER NOT NULL DEFAULT 0");
}
```

`pragma_table_info` — це запит до самої схеми, тож перевірка чесна: колонку
додаємо тільки якщо її справді немає. `DEFAULT 0` означає, що всі наявні
нотатки лишаються активними, а сідові дані й засіяні тести не змінюються.

## 2. Ендпоінт

```http
PATCH /api/notes/:id/archive
{ "archived": true | false }
```

`PATCH`, а не `POST`: це часткова зміна наявного ресурсу. Один ендпоінт на
обидва напрямки — стан передається в тілі, тому «архівувати» і «повернути з
архіву» не розповзаються на два майже однакові маршрути.

Відповідь — оновлена нотатка (`200`), щоб UI не робив зайвий запит по список.

## 3. Валідація на сервері

| Вхід | Відповідь |
|---|---|
| немає заголовка `x-user-id` | `401` |
| `:id` не додатне ціле (`abc`, `-1`) | `400` |
| `archived` не булеве (`"yes"`, `1`, немає поля) | `400` |
| нотатки немає **або** вона чужа | `404` |
| коректний запит | `200` + оновлена нотатка |

`archived` перевіряється саме на `typeof === "boolean"`, а не на
істинність: рядок `"false"` — це помилка клієнта, а не «хибне значення».
Мовчазне приведення типів тут ховало б баг у UI.

Перевірка навмисно дублює те, що вже не дає зробити інтерфейс: браузерний код
контролює користувач, тож обмеження, яке живе лише в UI, не є обмеженням.

## 4. Що ендпоінт не віддає

У відповідях немає `user_id` — внутрішня колонка, якої клієнт не потребує
(він і так знає, ким увійшов). Закріплено тестом, який звіряє **повний**
перелік ключів, а не лише відсутність одного поля: інакше наступне випадково
додане поле пройшло б непоміченим.

## 5. Фільтр списку

```http
GET /api/notes              → активні (параметр опущено)
GET /api/notes?archived=0   → активні — те саме, лише явно
GET /api/notes?archived=1   → лише архівовані
GET /api/notes?archived=all → усі
```

Валідних значень три: `0`, `1`, `all`. `archived=0` рівнозначне опущеному
параметру — саме його шле UI (`app/public/app.js`), щоб запит завжди
проговорював свій намір, а не покладався на замовчування сервера.

Будь-яке інше значення — `400`, а не мовчазне «покажемо все». Список тепер
віддає й саме поле `archived`, щоб UI міг намалювати бейдж і правильну кнопку.

За замовчуванням архівовані **сховані** — інакше фіча не мала б сенсу.

## 6. Тести

`app/test/archive.test.js` — 15 тестів: архівування й повернення, усі гілки
валідації, три режими фільтра, відсутність зайвих полів, і те, що відхилений
запит не змінює нотатку.

Авторизація цього ендпоінта перевіряється **окремо** — `app/test/authorization.test.js`
(Task C). Розділено навмисно: зелений набір «фіча працює» не повинен
виглядати як доказ того, що чужу нотатку зачепити не можна.

**Перевірено, що тести не бутафорські.** Тимчасово прибрали перевірку
`typeof archived !== "boolean"` — 3 тести одразу почервоніли; повернули —
знову зелено. Набір, який зеленіє за будь-якого коду, нічого не доводить.

```text
Test Files  2 passed (2)
     Tests  24 passed (24)     ← 9 засіяних + 15 нових
```
